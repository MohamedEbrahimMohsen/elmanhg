## Deviations
| Plan said | Reality | What I did |
|---|---|---|
| DG1/DG2 assert localised `feedback` over HTTP; only the listed test files change | `Core.Localization.Localizer` creates its `IStringLocalizer` from `Assembly.GetEntryAssembly()`. Under the test host the entry assembly is `Elmanhg.Tests`, so every resx lookup returned `""` (DG1/DG2 failed with `""`). No existing integration test asserted localised text, so this was latent. Production (entry = Elmanhg.Api) is unaffected. | Added `Integration/Infrastructure/ApiResourceStringLocalizerFactory.cs` (wraps `IStringLocalizerFactory`, redirects `Create(baseName, location)` to the Elmanhg.Api assembly name) and, in `ApiFactory.ConfigureTestServices`, `RemoveAll<ILocalizer>()` + `AddScoped<ILocalizer>(x => new Localizer(new ApiResourceStringLocalizerFactory(...)))`. No production or vendored code changed. DG1/DG2 kept exactly as specified. |

## Notes for review
- The two test-infra files above are the only departure from the plan's file list; they are test-only.
- `ChoiceGrader.GradeMulti` now checks for an empty selection before an empty correct set (plan order), so an empty correct set with no selection returns `Unanswered` instead of plain 0. The correct set is never empty after validation.
- The docs say feedback is "Arabic by default": that holds for configured environments (`CoreLocalization:DefaultLanguage = ar` in `appsettings.example.json`). The vendored code falls back to `en` when the key is missing (as in the test host). This is not new behaviour.
- `ApiResourceStringLocalizerFactory` has one comment that explains why it exists (a non-obvious invariant about the test host). The same pattern is used for comments in `ApiFactory`.
- `ChoiceGraderTests.cs` is ~190 lines because of the 20 required tests. Other test files in the repo are also over 100 lines.
