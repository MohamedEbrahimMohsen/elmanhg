# Plan — OTP delivery channels: WhatsApp (Meta), Email (Resend), SMS (disabled) (#171, E1.S6)

## Goal
After this ships, a student who signs in with a mobile number gets the 6-digit code on WhatsApp through the Meta WhatsApp Cloud API. SMS through a generic telecom HTTP gateway is the fallback, but it is off. A student with an email account can also ask for a one-time code by email (sent through Resend) and sign in with it instead of a password. The API reports which channel it used, and the code screen says "sent via WhatsApp", "sent by text message" or "sent to your email". Each channel is turned on and pointed at its provider through configuration only. `Fake` providers stay the default, so dev, tests and CI need no keys. If a real provider is enabled without its credentials, the app fails at startup.

## Scope
**In:** every sub-task of #171:
- a channel-agnostic `IOtpSender` / `IOtpChannel` in `Core.OTP` that replaces `ISmsSender`
- the `OtpDelivery` config section with per-channel `Enabled` / `Provider` / credentials and `DefaultPhoneChannel`, plus startup validation
- the Meta WhatsApp, Resend and generic HTTP SMS adapters, each a typed `HttpClient` with the standard resilience handler
- `FakeOtpChannel` as the default
- phone routing: WhatsApp, then SMS, then 503
- email OTP sending, plus a new `POST /api/auth/login/email-code` so the Email channel has a product use
- web: the OTP screen names the channel, and email sign-in gets a code option
- docs: PRD §7.1, `appsettings.example.json`, `.env.example`, the new `docs/otp-delivery.md` (config and go-live notes), README, backlog.json and Postman
- tests for request shapes (stub handler), routing, disabled channels and startup validation

This PR also resolves #137 (the deferred real SMS adapter): the generic HTTP adapter is that adapter.

**Out:**
- Meta delivery-status webhooks. Asynchronous "undeliverable" reports are not requested.
- Falling back from WhatsApp to SMS on a runtime *failure*. The story asks for fallback only when WhatsApp is *disabled*.
- Email-code sign-up. Email sign-up stays email and password.
- Email confirmation and password reset.

**Deferred (the orchestrator opens issues):**
1. **Live smoke test of the three real adapters** against Meta, Resend and a telecom. No credentials exist in this repo. The dev adds keys later, per `docs/otp-delivery.md`.
2. **Meta authentication template creation and approval, and the Resend sending-domain DNS verification.** Both are account actions in external consoles.
3. **Choice of Egyptian telecom and its concrete `BodyTemplate`.** Not chosen yet (dev decision). The adapter is generic and config-only.
4. **Production runbook entries.** The runbook is #112, which is not built yet. `docs/otp-delivery.md` lists every `OtpDelivery__*` variable, and #112 must link it.

## Decisions
| # | Question | Decision | Why |
|---|----------|----------|-----|
| 1 | What does the Email channel deliver to, given that email sign-in is password-based (#56)? | Add **email-code sign-in** for existing **student** email accounts: `otp/send` with `{ email }`, then `otp/verify`, then `POST /api/auth/login/email-code { verificationId }`. Password sign-in stays. Email sign-up stays password-only. | The story reads "I receive my sign-in code on WhatsApp (or email)", and the web sub-task needs a "sent to your email" state. Without a flow, the Email channel would be dead code. This is the smallest additive flow. |
| 2 | Can teachers and admins use email codes? | No. Code sign-in for a non-Student account → 403 `EMAIL_CODE_SIGN_IN_NOT_ALLOWED`. | The story is "As a student". #56 decision 1 says staff use email and password only. This keeps the staff attack surface unchanged. |
| 3 | Where does the abstraction live? | `Core.OTP/Delivery`: `OtpChannel`, `IOtpChannel`, `IOtpSender`. The router, fakes and adapters live in `Elmanhg.Infrastructure/OtpDelivery`. `Core.OTP/Sms/ISmsSender.cs` is deleted. | `ISmsSender` lived in `Core.OTP`, and `GenerateOTPHandler` consumes the port. Adapters are Infrastructure (constitution: external provider adapters). |
| 4 | How is an email OTP stored, given that the `Otp` entity is keyed by `PhoneNumber`? | Rename the property to `Recipient`, mapped with `HasColumnName("PhoneNumber")`, so the DB is not renamed. Add `OtpRecipientType RecipientType` (`Phone`, `Email`), stored as a string of max 50, with a migration default of `'Phone'` for existing rows. | Storing emails in `PhoneNumber` is a naming lie. A column rename is a destructive migration (skill §6.7). The discriminator stops an email-verified OTP from registering or logging in a phone account. |
| 5 | Wire shape of `otp/send` | `GenerateOTPCommand(string? PhoneNumber, string? Email = null)`. Exactly one must be set, otherwise 422 `OTP_RECIPIENT_REQUIRED`. The email is trimmed and lower-cased as the recipient key. | Additive. The existing web and Postman body `{ phoneNumber }` still binds, and existing tests compile unchanged thanks to the default. One rate-limit policy covers both. |
| 6 | How does the API report the channel? | `GenerateOTPResult` gains a final positional `OtpChannel Channel`, serialised as `"WhatsApp"`, `"Sms"` or `"Email"` (the JsonStringEnumConverter is already on MVC). | Web sub-task: "based on the channel returned by the API". |
| 7 | Routing rule | Email recipient: `Email.Enabled` → Email, otherwise 503. Phone recipient: `DefaultPhoneChannel` if enabled, then the other phone channel (WhatsApp↔Sms) if enabled, otherwise 503 `OTP_CHANNEL_UNAVAILABLE`. `DefaultPhoneChannel` = `WhatsApp` in committed config. `Email` as a default phone channel fails startup validation. | This is the story rule, generalised by config ("channel changes through config only"). |
| 8 | 503 exception | Add `ServiceUnavailableCoreException` (HTTP 503) to `Core.Errors/Exceptions.cs`, in the same shape as its siblings. | The story requires 503, and skill §5.9 has no 503 type. The rule "never add an exception for a status already listed" does not apply. |
| 9 | Provider failure mapping | In all three adapters, a non-2xx response, an `HttpRequestException`, a Polly `ExecutionRejectedException` (timeout or open circuit), and an `OperationCanceledException` not caused by the caller's token all become `ServiceUnavailableCoreException(ErrorCodes.OtpDeliveryFailed, innerException)`. Log at Error with channel and status code only: never the recipient, the code or the response body. | This is one client-facing outcome ("could not deliver, retry"). The skill §10 logging rule bans OTPs and PII. |
| 10 | Order in `GenerateOTPHandler` | Generate the code. Find or create the OTP (`Reissue` guards → 429). **Send** (routing, then provider). **Then** `SaveChangesAsync`. | If delivery fails, nothing is persisted, so the user is not locked in a 60 s cooldown for a code they never got. The rare "sent but save failed" case costs one resend. |
| 11 | Retries and timeouts | Each typed client gets `AddStandardResilienceHandler()`, configured from `OtpDelivery:AttemptTimeoutSeconds` (10) and `TotalTimeoutSeconds` (30). **Resend retries** POST because every request carries a fresh `Idempotency-Key` header (Resend supports it). **Meta and SMS call `Retry.DisableForUnsafeHttpMethods()`**. | Skill §8.8: POST retries only with an idempotency key. |
| 12 | Package | `Microsoft.Extensions.Http.Resilience` **10.10.0**, added to `api/Directory.Packages.props` and referenced by `Elmanhg.Infrastructure`. | Neither Morabh nor the repo has an HTTP client pattern. This is the Microsoft standard, and the version was verified with `dotnet package search`. |
| 13 | "Fake whenever credentials are missing" versus "startup validation" | `Provider` defaults to `Fake` in every committed config (example, ApiFactory, build-time OpenAPI). A real provider is chosen explicitly (`OtpDelivery__WhatsApp__Provider=Meta`), and then missing credentials **fail startup**. There is no silent auto-fallback to Fake. | Both sub-tasks hold: with no keys set, nothing is real, and a half-configured real provider cannot boot. `FakeOtpChannel` warns on every send outside Development. |
| 14 | Phone number format for Meta and SMS | `PhoneNumberFormatter.ToInternational("01012345678", "20")` → `"201012345678"`: the leading `0` is replaced with `OtpDelivery:CountryCallingCode`. The SMS template can use `{phoneNumber}` (local) or `{internationalPhoneNumber}`. | Meta requires digits in international form. The telecom format is unknown, so both are offered. |

When `CopyCodeButton` is true, a `button`/`url`/index `"0"` component also carries the code, as Meta authentication templates with a copy-code button require. | This is Meta's documented authentication-template send shape. |

## Domain behaviour
`Otp` (Core.OTP):
- `Create(recipientType, recipient, …)` sets `RecipientType = recipientType` and `Recipient = recipient`. Every other field is set exactly as today.
- `Reissue`, `Verify` and `MarkUsed` are unchanged.
- `Otp : Entity` has no `UpdationDate`, and none is added.
- `RecipientType` never changes after `Create`. There is no setter method.

No new aggregate. The User entity is unchanged: `Role` and `IsActive` are read by the handler.
