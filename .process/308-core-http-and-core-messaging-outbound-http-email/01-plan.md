# Plan — E21.S5 Core.Http and Core.Messaging: outbound HTTP, email/WhatsApp/SMS clients, OTP channels

## Goal
Pure refactor, no product change. Outbound HTTP plumbing that is copied across the app today (transient-failure filter ×10, JSON send-and-read ×6, `AddStandardResilienceHandler` timeout block ×8, `TrimEnd('/')` base addresses, the `Elmanhg/1.0` User-Agent that lives in the OTP namespace) moves into a new app-agnostic `Core.Http`. The Resend, Meta WhatsApp and generic HTTP SMS request builders move into a new `Core.Messaging`. `Core.OTP` gets the real channel adapters, the fallback router and the delivery options. The app passes in its error codes, email template and metrics. Afterwards a second app can send OTPs over WhatsApp, email or SMS using only `Core.*`. Every Elmanhg endpoint, payload, log-free behaviour and existing config key stays the same.

## Scope
**In:**
1. New `api/core-libraries/Core.Http`, with tests.
2. New `api/core-libraries/Core.Messaging`: `ResendEmailClient`, `MetaWhatsAppClient`, `HttpSmsClient`, `HttpSmsBodyRenderer` and `PhoneNumberFormatter`, with tests.
3. `Core.OTP/Delivery`: the WhatsApp, email, SMS and fake channels, `OtpChannelRouter`, `OtpDeliveryOptions` and its validator, and `AddCoreOtpDelivery(setup)`. The app keeps its templates, its `OtpDeliveryFailed` and `OtpChannelUnavailable` codes, and its metrics, passed in through `OtpDeliverySetup` and `IOtpDeliveryObserver`.
4. App changes:
   - One abstract `AiServiceHttpClient` base for the 6 AI HTTP clients.
   - One `AiJsonSerializerOptions.Default` instead of 5 copies.
   - `AddProviderSwitch` replaces the hand-written Fake/real switch in AI (×5), Payments (×1), Invitations (×1), Messaging (×2) and Core.OTP (×3).
   - Paymob, Invitations and Messaging use Core.Http and Core.Messaging.
5. Docs-sync, listed under Definition of done.

**Out:**
- `Core.Notifications` and `CoreDbContext` stay untouched (dev decision 2026-10-06).
- `Core.OTP/Entities/*`, `Core.OTP/Repositories/*`, `Core.OTP/DependencyInjection.cs` and `Program.cs` are not edited. Lane #304 owns them.
- `Elmanhg.Infrastructure/Storage/*`, `RichText/RichTextSanitizer.cs` and `Api/Hosting/ObservabilityExtensions.cs` are not edited. Lanes #310 and #313 own them, so the storage `TrimEnd('/')` and provider-switch copies stay for those lanes.

**Deferred:** none.

## Decisions
| # | Question | Decision | Why |
|---|----------|----------|-----|
| D1 | Morabh reuse | No Morabh equivalent exists: no HttpClient, resilience, Resend or WhatsApp code under `Morabh/repos/apis/Core` or the app layers (grep checked). Every new type is "new — no Morabh equivalent". The moved types keep their Elmanhg source as their origin. | Reuse-first check done. |
| D2 | How the User-Agent is made configurable | `CoreHttpOptions.UserAgent`, bound from section `CoreHttp`. `AddCoreHttp(string defaultUserAgent)` sets the default first, then binds config over it. The app calls `AddCoreHttp("Elmanhg/1.0")` from `AddInfrastructure`. `appsettings.example.json` gets `"CoreHttp": { "UserAgent": "Elmanhg/1.0" }`. A blank value sends no header. | Core gets no Elmanhg default. Existing hosts without the key keep sending `Elmanhg/1.0`. `Program.cs` is untouched because #304 edits it. |
| D3 | Where the UA is applied | Clients take `IOptions<CoreHttpOptions>` and call `request.WithUserAgent(...)` on each request: Core.Messaging clients, the AI base and Paymob. Not a DelegatingHandler. | The 7 existing unit tests build clients with `new HttpClient(stub)` and assert the UA header. With constructor injection they only gain one argument, and their assertions stay. |
| D4 | `SendJsonAsync` shape | One request record, `HttpJsonCall(Method, Path, Content, Authorization, UserAgent)`, with `Post<TRequest>` and `Get` factories. Two methods: `TrySendJsonAsync<TResponse>`, which never throws for transient, rejected or unreadable failures and returns `HttpJsonReply<TResponse>`, and `SendJsonAsync<TResponse>`, which throws `ServiceUnavailableCoreException(errorCode)`. | 4 AI clients throw. Math check and configuration return null/Unchecked and must keep doing so, with no catch-for-control-flow. |
| D5 | Messaging client failure semantics | Core.Messaging clients return `HttpSendResult`: `None`, `Rejected(status)` or `Unreachable(exception)`. Only `IsTransientFailure` exceptions become `Unreachable`; others propagate. Callers decide: OTP channels throw via `EnsureDelivered`, invitations return false, and reminders return false. Reminders also keep their catch-all `when (!ct.IsCancellationRequested)`. | These are the three different failure contracts that exist today, each preserved. |
| D6 | Who registers the transport typed clients | `AddCoreOtpDelivery` registers `MetaWhatsAppClient`, `ResendEmailClient` and `HttpSmsClient` once: base URLs from `OtpDelivery:*:BaseUrl`, resilience from `OtpDelivery:Attempt/TotalTimeoutSeconds`, retries on for Resend only. Invitations and reminders inject the same typed clients and no longer register their own. | Today all three Resend senders and both WhatsApp senders already use the same OTP base URL and OTP resilience settings, so the wire behaviour is identical. |
| D7 | `AddTimeoutResilience` circuit-breaker window | It sets the attempt and total timeouts. It raises `CircuitBreaker.SamplingDuration` to `attempt * 2` only when the default window is smaller. | Today: AI sets the window to 2×attempt, while OTP and Payments keep the default 30 s. With the max rule every client keeps its current window except `HttpAiConfigurationClient`, which goes from 10 s to the default 30 s. That is still valid and not observable by any endpoint. |
| D8 | Where `AddProviderSwitch` lives | `Core.Http`, not the app. | The story lists it under the app, but core placement lets `Core.OTP`'s 3 switches use it too: 12 copies collapsed instead of 9. It is app-agnostic. |
| D9 | Unknown enum provider values | The existing `InvalidOperationException("Unsupported <Section>:Provider.")` is kept. The selector lambdas `UsesHttp`/`UsesPaymob`/`OtpDeliveryProviders.Uses*` throw it inside `useReal`. | Behaviour unchanged. |
| D10 | Paymob | Gets only `IsTransientFailure`, `WithUserAgent`, `HttpBaseAddress.From`/`Combine`, `AddTimeoutResilience` and `AddProviderSwitch`. It keeps its own send/read code. | Refund splits 5xx/429 (503) from 4xx (400 declined), and its logs carry the PaymentId. `SendJsonAsync` cannot express that. |
| D11 | Log text of the AI clients | Thrown failures log at Error through `SendJsonAsync` with a generic template: `Outbound {Method} {Path} failed: {Failure}, HTTP {StatusCode}.` Math check logs Error, configuration logs Warning, as today. The "invalid reply" logs stay in the concrete clients. | Levels are unchanged, and `docs/math-cas.md` "logs an Error" stays true. No test asserts AI log text. |
| D12 | `MetaWhatsAppTemplateMessage.Create` (OTP) and `CreateUtility` (reminder) | Merged into one `Create(to, templateName, languageCode, bodyParameters, urlButtonSuffix)`. OTP passes `[code]` and `CopyCodeButton ? code : null`. | It produces the same JSON as today's OTP `Create`, which is covered by the moved `MetaWhatsAppOtpChannelTests`. |
| D13 | `PhoneNumberFormatter` trunk prefix `'0'` | Kept in Core.Messaging. The country calling code stays a parameter. | Trunk-prefix 0 is the ITU convention for most countries, so it is not Egypt-only. |
| D14 | Metrics callback | New `IOtpDeliveryObserver { void RecordOtpSend(OtpChannel channel, bool delivered); }` in Core.OTP. `ElmanhgMetrics` implements it, with no signature change. The router takes `IEnumerable<IOtpDeliveryObserver>`, so zero observers needs no null class. The app registers the observer as a forward to the `ElmanhgMetrics` singleton. | Metric name and tags are unchanged, and `OtpChannelRouterTests` metric assertions stay. |
| D15 | Moved tests | Moved with `git mv` into `Elmanhg.Tests/Core/{Http,Messaging,Otp/Delivery}/`. Names and assertions are unchanged; only constructors, usings and typed-client names are adapted. `StubHttpMessageHandler` and `OtpDeliveryTestSettings` stay in `Tests/Infrastructure/OtpDelivery/` because ~20 files import them. | Story: "moved code keeps its tests next to core coverage". |
| D16 | Core.OTP DI class name | `CoreOtpDeliveryServiceCollectionExtensions.AddCoreOtpDelivery`. | Avoids a clash with the app's `OtpDeliveryServiceCollectionExtensions.AddOtpDelivery`. |
| D17 | Package references | `Core.Http` gets `Microsoft.Extensions.Http.Resilience` `10.7.0` inline (already in the solution's CPM at the same version) and `FrameworkReference Microsoft.AspNetCore.App`. No new NuGet package. `Elmanhg.Application` now pulls Http.Resilience transitively via `Core.OTP`, which is accepted. | Core pins versions inline (`core-libraries/Directory.Packages.props`). |
| D18 | `HttpBaseAddress.Combine` adoption | Applied to `ResendEmailMessageChannel` (thread link), `FakePaymentGateway` and `PaymobIntentionRequest`. Storage and RichText copies are left for lane #310. | Lane isolation. |
