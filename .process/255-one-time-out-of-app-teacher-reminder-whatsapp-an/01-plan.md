# Plan — One-time out-of-app teacher reminder (WhatsApp and email) · #255 [E18.S3]

## Goal
When a student question in a teacher's subject reaches a configurable SLA reminder stage (default: the second reminder), the teacher who claimed it, or every teacher of the subject while nobody has claimed it, gets exactly **one** reminder outside the app, on WhatsApp and/or by email. This happens once per thread, across repeated sweeps, restarts, concurrent sweeps and follow-up windows. Admins switch it on or off and choose the channels and the stage on the Configuration page. The existing in-app reminders (SignalR toast and the «تذكيرات» card) do not change. Admins can also record an optional WhatsApp number for each teacher (on invite, or later from the teacher row), which the WhatsApp reminder needs.

## Scope
**In:**
- A small messaging port for non-OTP messages: `IMessageChannel` (Application), with Meta WhatsApp, Resend email and fake adapters (Infrastructure). The adapters reuse the #171 `OtpDelivery` credentials, typed-client resilience, `PhoneNumberFormatter`, `MetaWhatsAppTemplateMessage` and `ResendEmailMessage`.
- An idempotency marker table `TeacherThreadOutOfAppReminders` (unique `ThreadId`). It is written in the same `SaveChangesAsync` as the SLA event rows.
- The send step in `ProcessTeacherThreadSlaHandler`: two touch points, both at stage level.
- Three runtime settings in the AskTeacher group (enabled, channels, stage). Two read-only integration rows on the Configuration page.
- **Teacher WhatsApp number capture (coordinator amendment):** an optional `PhoneNumber` on the teacher, validated exactly like the student phone-OTP flow (`ValidatePhoneNumber(CoreOtp:PhoneCodes, CoreOtp:PhoneLength)`, web `egyptianMobilePattern`). The admin sets it in the invite dialog (teachers only) and sets, changes or removes it from the teacher row on `/admin/users` (`PUT /api/teachers/{teacherId}/phone-number`). It is audited as `Teacher.SetPhoneNumber` and never logged. Admin-only: there is no teacher profile or settings page today (`/teacher/more` is a nav overflow list).
- The WhatsApp utility template (configurable name, language and thread-link button) and an ar/en email template.
- Options plus startup validation, appsettings example, api.env example, and docs (PRD, ask-teacher, otp-delivery, configuration, deployment, implementation-report).
- Tests: .NET unit, infrastructure, integration and web.

**Out:**
- Getting the Meta utility template approved. This is a go-live step for the dev and is documented in `docs/otp-delivery.md` §10.
- Changes to the in-app reminders, the SLA stage times (owned by #254) and the worker loop.
- SMS for reminders. SMS stays an OTP-only fallback.
- Per-user language preference. No user language exists, so the email language is a deployment setting.

**Deferred:**
- **Real Meta/Resend delivery check.** No credentials exist here. The real adapters are built and tested against a stubbed `HttpMessageHandler`, as #171 did.

## Decisions
| # | Question | Decision | Why |
|---|----------|----------|-----|
| 1 | Where does the "once per thread" marker live? | A new append-only entity `TeacherThreadOutOfAppReminder` (table `TeacherThreadOutOfAppReminders`) with a **unique index on `ThreadId`**. There is no column on `TeacherThread`. | `TeacherThread` carries an xmin token, and `docs/ask-teacher.md` §SLA states "the worker never writes TeacherThreads, so it cannot bump a thread's xmin under a teacher's reply". A column there would let the sweep 409 a teacher's concurrent claim or reply. A 1:1 row keyed by thread id is still "the marker on the thread". |
| 2 | How is it exactly-once across concurrent sweeps and restarts? | The marker is added in the **same `SaveChangesAsync`** as the newly due SLA event rows, so it is one transaction. A concurrent sweep loses on the unique `(ThreadId, Kind, SlaDueAt)` event index or the unique marker index and saves nothing. Only the caller whose save succeeded sends. After a restart, the marker row exists (`IsRecordedAsync`), so nothing is sent again. A follow-up window's stages fire again, but the marker blocks a second out-of-app send. | Reuses the #97 exactly-once mechanism and needs no lock. |
| 3 | Mark before or after sending? | Mark (commit), **then** send: at-most-once. A crash between commit and send loses that one reminder. The in-app reminder still covers it. | The story requires "once". A duplicate WhatsApp to a teacher is worse than a missed one, and the in-app path remains. |
| 4 | Hook into the SLA sweep (#254 coordination) | Stage level only. The hook reads `missing` (the stages this call newly records). If the configured stage is in `missing`, it claims and dispatches. It never reads or computes times. Touch points in `ProcessTeacherThreadSlaHandler`: **A** = one `ClaimAsync` statement after the `foreach AddAsync` loop and before `SaveChangesAsync`. **B** = one `SendAsync` statement after `NotifyReminderAsync`. Constructor plus 3 dependencies. `TeacherThread.DueSlaStages`, `GetSlaDueIdsAsync` and the worker are untouched. | #254 owns the time maths. These three edits are the only merge surface. |
| 5 | Which deadline does the message show? | `thread.SlaDueAt` (whatever #254 stores there), converted to `OutOfAppReminders:TimeZone` (default `Africa/Cairo`) and formatted `yyyy-MM-dd HH:mm`. | It is the stored deadline that the inbox badge also uses. |
| 6 | Abstraction: extend `IOtpChannel` or a new one? | New Application port `IMessageChannel { MessageChannel Channel; Task<bool> SendAsync(OutboundMessage, CancellationToken) }`. `OutboundMessage` is an abstract record, and `TeacherThreadReminderMessage` is the first concrete message. Each adapter renders a message type with its own template. An unknown type throws `NotSupportedException`. | `IOtpChannel` is vendored Core (`Core.OTP.Delivery`) with an OTP-shaped `(recipient, code)` signature and throws 503 codes. Changing Core is out of bounds. A second message type later adds one record and one template case per adapter. Morabh has nothing reusable (see Morabh reuse). |
| 7 | Failure isolation | Adapters **never throw** for provider faults. Any exception during the HTTP send (except cancellation) and any non-2xx response are logged as a Warning and return `false`. This mirrors `SignalRTeacherThreadNotifier` best-effort and `ResendInvitationEmailSender`. The dispatcher loops recipient × channel sequentially, and one `false` does not stop the others. The sweep item does not fail. | Story: "if one channel fails, the other still sends and the sweep does not fail". |
| 8 | Logging | Logs carry the thread id, user id, channel, message type, HTTP status and outcome. They **never** carry the phone, the email address, the token, the API key or the message body. One log line per attempt: Information when delivered or skipped, Warning when failed. | Story and `docs/security.md` logging rule. |
| 9 | Recipients | `TeacherThreadReminderRecipients.LoadAsync` (unchanged: the claimer, otherwise every teacher assigned to the subject). The users are loaded once with `FindAsync(ids.Contains(Id) && Status == Active && PasswordHash != null)`, so suspended teachers and teachers whose invitation is still pending are not messaged. | Reuses the in-app recipient rule. A pending invitee has no account yet. |
| 10 | No phone or no email | WhatsApp uses `User.PhoneNumber`, Email uses `User.Email`. A blank value skips that channel for that user, with an Information log "no contact on file". The other channel still sends. Teachers always have an email. A teacher has a phone only when an admin set one (Decision 22). | Story asks to state it. |
| 11 | No recipients at the trigger stage | The marker is still recorded and nothing is sent. | It matches the in-app rule "with no recipients the event is still recorded". The stage has passed. |
| 12 | Settings | Runtime settings (#253), group `AskTeacher`, in class `OutOfAppReminderRuntimeSettings`: `askTeacher.outOfAppReminderEnabled` (Boolean, default `true`), `askTeacher.outOfAppReminderChannels` (Choice `WhatsApp` / `Email` / `Both`, default `Both`), `askTeacher.outOfAppReminderStage` (Choice `FirstReminder` / `SecondReminder`, default `SecondReminder`). Defaults come from `AskTeacherOptions`. | A single Choice instead of a ChoiceList avoids an "enabled with zero channels" state (no constraint, no error code). It also avoids the `ConfigurationBinder` array-append gotcha with a defaulted array. `Breach` is excluded because the story says "close to its deadline". A separate definitions class keeps `AskTeacherRuntimeSettingsTests.Constraints.Single()` true. |
| 13 | Template name, language, link: runtime setting or deployment configuration? | Deployment configuration, section `OutOfAppReminders` (Infrastructure Options). | They are tied to a Meta approval and the site host. `docs/configuration.md` §7 keeps infrastructure out of runtime settings. |
| 14 | WhatsApp adapter selection | Meta when `OtpDelivery:WhatsApp` is `Enabled` with `Provider=Meta` **and** `OutOfAppReminders:WhatsAppTemplateName` is not blank. Otherwise the fake. The fake logs a Warning on every send outside Development, and the infrastructure row shows the mode `Fake`. | OTP go-live must not be blocked on a second template approval. The state stays visible on the Configuration page and in the logs. |
| 15 | Email adapter selection | Resend when `InvitationEmailServiceCollectionExtensions.UsesResend(OtpDelivery:Email)`. Otherwise the fake. With Resend on, `OutOfAppReminders:ThreadLinkBaseUrl` must be an absolute https URL or the boot fails. | Mirrors the `InvitationEmail:AcceptInviteUrl` precedent (#240). |
| 16 | Email language | `OutOfAppReminders:EmailLanguage` `ar` (default) or `en` picks the template pair and the subject (`EmailSubjectArabic` / `EmailSubjectEnglish`). | Users have no language field. Story: "Email uses an ar/en template". |
| 17 | WhatsApp template variables | UTILITY category. Body `{{1}}` subject name, `{{2}}` lesson name, `{{3}}` deadline. When `WhatsAppThreadButton=true`: a URL button at index 0 whose dynamic suffix is the thread id (the Meta-side URL is `https://<SITE_ADDRESS>/teacher/thread/{{1}}`). Names come from `TeacherThread.ReadContext()` (stored strings, no lookup). | Web route `/teacher/thread/$threadId` exists. Same button component shape as the OTP copy-code button. |
| 18 | Retries | Meta: no retry for POST (`AddOtpResilience(retryUnsafeMethods: false)`), as for OTP. Resend: retried, with a **deterministic** `Idempotency-Key` `teacher-reminder-{threadId:N}-{userId:N}`. | Resend dedupes identical keys, which gives a second guard against duplicate email. |
| 19 | Configuration page | The three settings render automatically in the AskTeacher card. Web adds the `choices.*` labels. Infrastructure gets two rows, `teacherReminderWhatsApp` and `teacherReminderEmail`, inserted after `invitationEmail`. | Story: "Settings and Configuration page entries". |
| 20 | Metrics | None added. Logs only. | Not asked for. It avoids an observability-doc change. |
| 21 | Messaging doc | A new §10 in `docs/otp-delivery.md` ("Non-OTP messages: teacher reminders"), plus an intro sentence. No new doc. | Same adapters and same config section family. The story allows either place. |
| 22 | Where is the teacher's WhatsApp number stored? | The existing `User.PhoneNumber` (Identity column), set only through the new domain method `User.SetContactPhoneNumber`. `PhoneNumberConfirmed` stays `false`. There is no new column and no migration for it. | The column already exists and is what the reminder reads (Decision 10). The number is not verified by OTP, and the coordinator asked for the smallest change. |
| 23 | Can a teacher's number enable phone sign-in or clash with a student? | No. Phone sign-in and registration look up `FindByNameAsync(otp.Recipient)`, and a teacher's `UserName` is the email, so a teacher number never signs anyone in and never blocks a student registration. There is no uniqueness check, so a teacher may share a number with their own student account. Test 74 proves phone sign-in still returns 404. | Keeps the auth surface unchanged. |
| 24 | Validation | It is the same as student phone OTP: `RuleFor(x => x.PhoneNumber).ValidatePhoneNumber(otpOptions.PhoneCodes, otpOptions.PhoneLength)` inside `When(x => x.PhoneNumber is not null)` (Core.Validation, codes `VALIDATION_PHONE_NUMBER_*`, 422). The web uses `egyptianMobilePattern` (exported from the `session` barrel) and the message `users:validation.phone`. The value is stored trimmed. | Amendment: "validated in the same format the student phone-OTP flow uses". |
| 25 | Endpoints | Invite: `InviteUserCommand` gains the optional `string? PhoneNumber = null` (last positional, so existing callers compile). A non-null value with `Role == Admin` → 422 `PHONE_NUMBER_TEACHERS_ONLY`. Edit: `PUT /api/teachers/{teacherId}/phone-number` with body `{ "phoneNumber": "010…" or null }` (null removes it), policy `Users.Manage`, 200 empty. A non-teacher id → 400 `PHONE_NUMBER_TEACHERS_ONLY` (domain guard). An unknown id → 404 `USER_NOT_FOUND`. A failed `UpdateAsync` → 409 `USER_MODIFIED_CONCURRENTLY` (the `SuspendUserHandler` pattern). | It sits next to the existing teacher-subject routes in `TeachersController`, which use the same policy. |
| 26 | Audit, and "never logged" | `SetTeacherPhoneNumberCommand : IAuditableCommand` (`Teacher.SetPhoneNumber`, resource type `Teacher`, resource id = TeacherId, mirroring `Teacher.AssignSubject`). `User` is not an `IAuditedEntity`, so the audit row has **no diff** and the number never reaches the audit table. The invite stays `User.Invite`, also without a diff. No `ILogger` call gets the number. Lists keep returning only `maskedPhone`. | Audited, never logged, never returned in full (`docs/user-administration.md` masking rule). |
| 27 | Admin UI | Invite dialog: an optional «رقم واتساب (اختياري)» field, shown only for teacher invites. Teacher rows on `/admin/users` get a secondary button «رقم واتساب» that opens `TeacherPhoneDialog`. The dialog shows the current masked number or «لا يوجد رقم.», a new-number field and Save, plus «حذف الرقم» when a number exists. The full number is never shown back. | It is the smallest UI on the existing teacher-management page. The masked value is the only one the API returns. |
| 28 | Teacher self-service | Not built: no teacher profile or settings page exists. | The coordinator allowed admin-only in that case. |

## Domain behaviour
```csharp
public static TeacherThreadOutOfAppReminder Record(Guid threadId, TeacherThreadSlaEventKind stage, DateTimeOffset slaDueAt, DateTimeOffset occurredAt)
{
    if (stage == TeacherThreadSlaEventKind.Breach)
    {
        throw new ArgumentOutOfRangeException(nameof(stage), stage, "The out-of-app reminder goes out at a reminder stage, never at the breach.");
    }

    return new TeacherThreadOutOfAppReminder(Guid.NewGuid())
    {
        ThreadId = threadId,
        Stage = stage,
        SlaDueAt = slaDueAt,
        OccurredAt = TeacherThread.ToMicroseconds(occurredAt),
    };
}
```
Append-only, with no mutators. `Entity` has no `UpdationDate`, the same as `TeacherThreadSlaEvent`. The guard is a programming-error guard (`ArgumentOutOfRangeException`, as in `TeacherThread.Rate`), not a business rule.

`User.SetContactPhoneNumber` (in `User.Administration.cs`):
```csharp
public void SetContactPhoneNumber(string? phoneNumber, Guid updatedBy)
{
    if (Role != UserRole.Teacher)
    {
        throw new BusinessRuleViolationCoreException(ErrorCodes.PhoneNumberTeachersOnly);
    }

    PhoneNumber = string.IsNullOrWhiteSpace(phoneNumber) ? null : phoneNumber.Trim();
    PhoneNumberConfirmed = false;
    UpdatedBy = updatedBy;
    UpdationDate = DateTimeOffset.UtcNow;
}
```

`ProcessTeacherThreadSlaHandler`: the final constructor (#253 baseline plus 3 dependencies, inserted after `teacherThreadNotifier`):
`public sealed class ProcessTeacherThreadSlaHandler(ITeacherThreadRepository teacherThreadRepository, ITeacherThreadSlaEventRepository teacherThreadSlaEventRepository, ITeacherSubjectRepository teacherSubjectRepository, ITeacherThreadNotifier teacherThreadNotifier, ITeacherThreadOutOfAppReminderRepository teacherThreadOutOfAppReminderRepository, IUserRepository userRepository, IEnumerable<IMessageChannel> messageChannels, ElmanhgMetrics metrics, IRuntimeSettings runtimeSettings, TimeProvider timeProvider, ILogger<ProcessTeacherThreadSlaHandler> logger) : IRequestHandler<ProcessTeacherThreadSlaCommand>`

Ordered `Handle` steps (only the **bold** steps are new):
1. Load the thread with no tracking. Return if it is null.
2. Get `now` and the runtime `values`. `due = thread.DueSlaStages(...)` (#254 owns this line). Return if empty.
3. Load the recorded events. `missing = due.Except(recorded kinds)`. Return if empty.
4. `foreach (kind in missing) AddAsync(TeacherThreadSlaEvent.Record(...))`.
5. **Touch point A:** `var outOfAppChannels = await OutOfAppTeacherReminder.ClaimAsync(thread, missing, values, teacherThreadOutOfAppReminderRepository, now, cancellationToken).ConfigureAwait(false);`
6. `await teacherThreadSlaEventRepository.SaveChangesAsync(cancellationToken)`. This one save persists the events and the marker atomically.
7. Metrics, and the breach Warning log (unchanged).
8. `reminders` (non-breach). Return if empty. `recipients = TeacherThreadReminderRecipients.LoadAsync(...)`. Return if empty. `NotifyReminderAsync` (unchanged).
9. **Touch point B:** `if (outOfAppChannels.Count > 0) { await OutOfAppTeacherReminder.SendAsync(thread, recipients, outOfAppChannels, userRepository, messageChannels, logger, cancellationToken).ConfigureAwait(false); }`
