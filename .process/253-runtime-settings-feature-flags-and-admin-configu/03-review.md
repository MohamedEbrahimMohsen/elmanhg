# Review — Runtime settings, feature flags and admin Configuration page (#253, E18.S1)

## Blocking

### 1. The D7 "reset when not overridden" branch is untested on its real path (an existing row whose value is already null)
**Where:** `api/Elmanhg.Application/Configuration/ResetRuntimeSetting/ResetRuntimeSettingHandler.cs:26`; `api/Elmanhg.Tests/Application/Features/Configuration/ResetRuntimeSetting/ResetRuntimeSettingHandlerTests.cs:53-61`; `api/Elmanhg.Tests/Integration/Configuration/ConfigurationEndpointTests.cs:149-159`
**Rule:** plan Decision D7 ("no write, no cache clear, no constraint check; audit row has no diff"); reviewer order #5 (would the test fail if the code were wrong?); docs/audit-log.md ResetRuntimeSetting row.
**Problem:** Reset never deletes the row (D1), so once a setting has been reset, every later reset of it runs with `row != null && row.Value == null`. Neither `Handle_NotOverridden_ReturnsDefaultWithoutSaving` nor `PostReset_NotOverridden_Returns200Unchanged` covers that case. Both use a key with no row at all. The implementer confirmed that the mutant `row?.Value is null` -> `row is null` survives the whole suite.
**Failure:** With that mutant, an admin clicks Reset twice, or resets a setting that was reset earlier. `row.Reset(userId)` runs again, `UpdatedBy` and `UpdationDate` change, `SaveChangesAsync` writes, the audit row records a change, and the shared cache is cleared. That breaks D7 and the documented "writes no change and the row has no diff". No test fails.
**Fix:** Add a unit test (for example `Handle_AlreadyReset_ReturnsDefaultWithoutSaving`). It should seed a row created with "12" and then `Reset(AdminId)`, call Reset again, and assert: `IsOverridden` false, `SaveChangesAsync` `DidNotReceive()`, the cache entry is still present, and `row.UpdationDate` is unchanged. Optionally add the same check to the endpoint test: reset twice, then expect exactly one `RuntimeSetting.Reset` audit row with a diff.
