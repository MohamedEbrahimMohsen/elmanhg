# Review — [E14.S3] Student essay input (#119)

## Blocking

### 1. `GET essay-grade` says `Graded` before the grade is applied, so `onGraded` can refresh too early and leave the score stale
**Where:** `api/Elmanhg.Application/EssayGrading/Shared/EssayGradeResultGenerator.cs:10` (status mapped straight from `grade.Status`), `api/Elmanhg.Api/Workers/EssayGradingWorker.cs:75-76` (two saves), `web/src/features/quiz/hooks/useEssayGrade.ts:9,14` (polling stops at `Graded`, and `onGraded` fires once)
**Rule:** plan Decision 4 and Decision 13, which rely on "Graded ⇒ the attempt and score exist". Gate 2 changed the design into two saves, but the read was not changed to match. `docs/essay-grading.md` § Student input says "`onGraded` refreshes the session score when the grade lands".
**Problem:** With the Grade→Apply split, a grade can be `Graded` while `AppliedAt` is null. The web treats `Graded` as final: it stops polling, runs `onGraded` once and refetches the session. If that refetch lands before Apply commits, nothing ever refetches again, because the result pages use `staleTime: Infinity` and polling has stopped.
**Failure:** Apply loses the `xmin` race to the student’s `/finish` (or the worker process stops between the two saves). The grade stays `Graded` with `AppliedAt` null until the next sweep, up to 10 s later. The client polls, gets `Graded`, runs `onGraded`, and refetches a session with `attempt: null` and a `scorePercent` that leaves the essay out. The quiz or exam result page then shows the final verdict next to the old score and the "still being graded" note, until the student reloads manually. On the normal path the same window lasts for the length of the Apply transaction, about one poll in a hundred.
**Fix:** Make the read reflect `AppliedAt`. In `EssayGradeResultGenerator.Generate`, return the `Pending` shape (no score) while `grade.IsAwaitingApplication`. Polling then continues, and `Pending → Graded` is only seen once the attempt exists. Add a `GetEssayGradeHandler` test for "Graded but not applied → Pending". Update the #118 tests that seed `Graded` grades so they call `MarkApplied`. Update the GET paragraph in `docs/essay-grading.md` ("`Graded` once the grade is applied to the session").

### 2. Postman "Submit essay answer" fails in the collection’s own run order, and `essayQuestionId` is declared twice
**Where:** `postman/elmanhg.postman_collection.json:1753` (Start quiz sets `essayQuestionId` to an empty string when no essay is served), `:1828-1852` (Submit essay answer), `:26` (second `essayQuestionId` variable; `:19` already existed)
**Rule:** Review order #7 (the request must be plausible and must run against its own flow), and PROGRESS "Postman … order them to respect state transitions".
**Problem:** The collection creates the essay question (`:1131`) but never approves it. "Approve question" at `:1622` approves `{{questionId}}`, which is the MCQ. So the essay is never servable, the quiz never contains it, and Start quiz sets `essayQuestionId` to an empty string. The new request then posts an empty `questionId`, which `SubmitAnswerRequest(Guid QuestionId, …)` cannot bind, so the API returns 400. The test only accepts `[200, 404]`. Separately, once an essay is servable, `sessionQuestionId = json.items[0].questionId` (`:1751`) can point at the essay, and "Submit answer" with `{optionId}` would then get 422.
**Failure:** Run the collection top to bottom. "Submit essay answer" returns 400 and its test fails.
**Fix:** Add a pre-request script to "Submit essay answer" (and "Get essay grade") that calls `pm.execution.skipRequest()` when `essayQuestionId` is empty. Alternatively, add an "Approve essay question" step. In Start quiz, set `sessionQuestionId` from the first item whose `type` is not `Essay`. Delete the duplicate variable at `:26`.

### 3. docs/sessions.md still says `AnswerSavedAt` is exams only
**Where:** code: `api/Elmanhg.Domain/Sessions/Session.Essays.cs:35` (`item.SaveAnswer(answer, now)` on a quiz essay sets `AnswerSavedAt`). Doc: `docs/sessions.md` § Data model, the `SessionItem` table row `AnswerSavedAt` (line 37): "Exams only: when the draft was last saved."
**Rule:** `.claude/rules/docs-sync.md` (divergence). The row above it (line 36) already gives the other answer.
**Failure:** Ask "is `AnswerSavedAt` set on quiz items?" The code says yes (the submission time of a pending essay); the doc says exams only.
**Fix:** Change the row to "Exams: when the draft was last saved. Quizzes: when a written essay was submitted."

## Non-blocking
- **(a) Ruling on `Sessions:EssayAnswerMaxLength` = 121000: the design is correct and safe.** The 20 000 limit the student sees is checked on the decoded text: `QuestionAnswerRules.IsEssayTooLong` (`QuestionAnswerRules.cs:45`) reads `EssayAnswer.Text.Length`, the untrimmed UTF-16 length, the same unit the textarea `maxLength` counts. The raw check (`IsRawAnswerTooLong`, `:47`, on `GetRawText()`, which keeps `\uXXXX` escapes) is only a request-size guard: 121000 = 20 000 × 6 + the envelope, and 6 is the worst case JSON escape (surrogate pairs are 12 characters for 2 units, the same ratio). Browsers send unescaped UTF-8, so a real 20 000-character essay is about 20 011 raw. Storage is bounded by the decoded and trimmed text (at most 20 000 characters in `SavedAnswer`, `EssayGrade.Answer` and `Attempt.Answer`). Non-essay answers keep the 4000 raw cap (gate 1), and a test covers it (`Handle_NonEssayOverAnswerCap_ThrowsAttemptAnswerTooLong`, `PostAnswer_McqOver4000Characters_Returns422AttemptAnswerTooLong`). DoS exposure is 121 KB of JSON per request, which is small. `docs/sessions.md`, `docs/exams.md`, `docs/essay-grading.md` and `appsettings.example.json` all agree with the code. Two refinements:
  - `SessionsOptions.cs:21` does not tie `EssayAnswerMaxLength` to `Content:QuestionEssayAnswerMaxLength`. A startup check `EssayAnswerMaxLength >= 6 × QuestionEssayAnswerMaxLength + 11` would stop an operator from raising one without the other.
  - For non-essay types, the per-type raw check now runs after the free-tier gate and the DB loads (`SubmitAnswerHandler.cs:65`). An oversized MCQ answer can therefore get 403 before 422 and costs a few queries.
- **(b) Ruling on the two-step grade→apply design:** the split itself is correct and needed for gate 2. The read must reflect `AppliedAt`; see Blocking #1.
- **(c) Training-record single write is verified.** `DomainEventDispatcher.PublishAsync` runs inside `CoreDbContext.SaveChangesAsync` before the base save. `AttemptTrainingRecordHandler` adds its row to the same context, so the attempt, mastery, training row and `AppliedAt` commit or roll back together. On retry, `RecordEssayAttempt` returns null when the attempt exists (`Session.Essays.cs:43-45`), so there is no second event. `GradeEssay_AppliedTwice_WritesOneAiTrainingRecord` proves this against Postgres.
- **(d) Quiz chunk at 254/255 KB br, 1 KB of headroom.** It passes today. Lane #122 also adds to the quiz page, so the lane that merges second will very likely go over budget. Suggested mitigation before or with #122: lazy-load `QuizEssayCard` (and with it `EssayGradeStatus`/`EssayGradeOutcome`) from `QuizRunner.tsx:25` via `React.lazy`, since only essay items need it. In any case, re-run `perf:budget` after merging `origin/main` into whichever lane lands second. Do not raise the budget.
- `api/Elmanhg.Infrastructure/EssayGrading/EssayGradeRepository.cs:14-15`: Graded-but-unapplied grades are listed first, and a failing Apply retries every sweep without a cap. With `SweepBatchSize` 5, five grades whose Apply fails every time would block all `Pending` grading. No realistic poison cause is known today (`GetPlacementsAsync` ignores query filters), but a retry cap or ordering them after `Pending` would remove the head-of-line risk.
- `api/Elmanhg.Application/Sessions/SubmitAnswer/QuizEssaySubmission.cs:22`: the `QUESTION_NOT_FOUND` throw has no test. The FK restrict makes it effectively unreachable.
- `api/Elmanhg.Domain/Sessions/Session.Essays.cs:61-67`: the `EnsureOwnItem` guard has no test.
- `docs/sessions.md:39`: "an exam item’s saved answer does [change]". A quiz essay’s `SavedAnswer` is also written after the session starts.
