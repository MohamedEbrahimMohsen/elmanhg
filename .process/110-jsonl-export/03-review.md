# Review — [E12.S2] JSONL export (+ #229 essay-grade training records)

## Blocking

### 1. Upload-then-save leaves export files that the retention sweep can never delete (gate condition 3)
**Where:** `api/Elmanhg.Application/TrainingExports/RunTrainingExport/RunTrainingExportHandler.cs:38-42`, `api/Elmanhg.Infrastructure/TrainingExports/TrainingExportRepository.cs:27`, `api/Elmanhg.Infrastructure/Storage/LocalDiskFileStorage.cs:13-14`; documented as accepted in `docs/training-data.md` § Export, Known limits (line 115).
**Rule:** `00-acceptance.md` gate condition 3 overrides the plan: export files have a short retention and a sweep deletes them. Plan D13 accepted orphans, but it was written before that gate condition existed.
**Problem:** The storage key exists only in memory until the final `SaveChangesAsync`. The file is written at :39. If anything fails between :39 and the commit at :42, no row points at the file. The retention query only selects `Status == Completed && ExpiresAt <= now`, so the sweep never sees it. That file of pseudonymised student text then stays in private storage indefinitely, which is the opposite of what gate 3 promises. This is not only a crash edge case. The same thing happens in ordinary failures: the host stops during a deploy and `stoppingToken` cancels the save, a transient DB error hits the save, or a second replica loses the `xmin` race. It also happens when an upload is cancelled half-way on Local, because `CreateNew` plus `CopyToAsync` leaves a partial file. In every case the worker retries under a new random key, so each failed attempt adds another orphan.
**Failure:** A `RunTrainingExportCommand` whose `SaveAsync` succeeds but whose `SaveChangesAsync` throws (for example, `stoppingToken` is cancelled on shutdown) leaves `training-exports/{id:N}-{r1:N}.jsonl` behind. The retry then completes with `{r2}`, and 7 days later the sweep deletes only `{r2}`. `{r1}` is never deleted.
**Fix (cheap, and it also closes the replica race):** Record the key on the export before uploading. Add a domain method such as `BeginRun(key, at)` that, while the export is still Pending, sets `FileKey` (or a separate `PendingFileKey`), then call `SaveChangesAsync`. That save becomes the `xmin` claim: a replica that loses it throws before it uploads anything. After that, upload, `Complete`, and save. When a retried run finds a `FileKey` left by an earlier attempt, it should `DeleteAsync` that key first; deleting is idempotent on both adapters. Also either delete the key when `FailAttempt` marks the export `Failed`, or widen `GetExpiredIdsAsync` to include `Failed` rows that still carry a `FileKey`. Add a handler test for "save fails after upload, the next run deletes the previous key", and remove the orphan bullet from Known limits.

## Non-blocking
- `api/Elmanhg.Application/TrainingExports/Shared/TrainingDataScrubber.cs:49`: the GUID/ISO exemption applies to every string inside the JSON columns, including student-typed text (answer JSON, thread message `text`). A string that is exactly ISO-shaped passes through untouched, and the regex does not check value ranges. A 14-digit national ID typed deliberately as `2990-10-12T34:56:78` fits the shape. This only matters for deliberate obfuscation; accidental PII never looks like this. Tightening it by key (exempt only structural keys such as `sentAt` or `*Id`) would close the gap. Also note that JSON numbers are never scrubbed (`ScrubJson_NonStringValues_Unchanged`), so a numeric answer holding a phone number passes through.
- `api/Elmanhg.Application/TrainingExports/Shared/TrainingExportJson.cs:9`: the WHY comment says the file is served with nosniff, but `TrainingExportsController.cs:42` sets only `Cache-Control`. Nothing global sets `X-Content-Type-Options`; only the media middlewares do. Exploitability is nil (the endpoint needs a bearer token and returns an attachment), but either set `Response.Headers.XContentTypeOptions = "nosniff"` or correct the comment.
- `api/Elmanhg.Application/TrainingExports/ExpireTrainingExport/ExpireTrainingExportHandler.cs:13-16`: the no-op returns (unknown or not yet expired) still produce a `TrainingExport.Expire` Success audit row through `AuditBehaviour`. The worker only sends ids that are already expired, so this is noise at most.
- `api/Elmanhg.Api/Workers/TrainingExportRetentionWorker.cs:140-144`: when listing fails, `exportIds` becomes empty, which clears `_deferredIds`. It is harmless, but a listing error should probably not reset the deferral.
- `api/Elmanhg.Domain/TrainingExports/TrainingExport.cs:28`: `DownloadFileName` formats the UTC `From`/`To`. A Cairo admin who picks 2026-01-01 sends `2025-12-31T22:00Z`, so the file is named `...-2025-12-31-...`. Cosmetic.
- `GET /api/training-exports` (list) is not audited. That matches the plan and the gate, which audit only request and download. Mentioned only because the brief asked about it.
- `RunTrainingExportHandlerTests` exercises only the `Attempts` branch of the source switch (`RunTrainingExportHandler.cs:27-34`). If two sources were swapped, no unit test would fail. `TrainingExportLineGeneratorTests` covers the per-source lines.
- `web/src/features/trainingExport/api/downloadBlob.ts:10`: `revokeObjectURL` runs synchronously after `click()`. This matches the existing questions helper, but older Safari can cancel the download. Deferring it with `setTimeout` would be safer.
