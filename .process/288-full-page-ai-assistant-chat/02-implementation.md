## Deviations
| Plan said | Reality | What I did |
|---|---|---|
| F15: `AssistantChat` calls `dispatch({ type: 'newChat', context })` through `useAvatar()` | `useAvatar().dispatch` is typed `Dispatch<AvatarAction>`, and `'newChat'` is not an `AvatarAction`. This would need a cast, and the plan forbids casts | `AssistantChat` calls `open(context)` from `useAvatar()` instead. The page's controller defines `open` as `dispatch({ type: 'newChat', context })`, so the behaviour is the same and the types are clean |
| F9 step 6: the phase is `'loading'` whenever `openingId !== null` | During an exam on `/student/assistant/X`, `opening(X)` is dispatched and the detail query is disabled, so the page would stay on «Opening the chat…». That contradicts D10, the scenario table ("the chat column shows the exam notice") and T14 | The phase is `'idle'` when `openingId === null \|\| !canLoad` |
| F17: the focus effect has deps `[blocked, form]` | When `blocked` turns false, RHF re-enables the input in a later render, so `setFocus` ran on a still-disabled input and focus stayed on «Send» (T13 failed) | The condition is `!blocked && !isSubmitting && sentRef.current`, with deps `[blocked, isSubmitting, form]`. `isSubmitting` turns false only after `form.reset()` and the list invalidation, when the input is enabled again |
| F13: `goToPage(page - 1)` is called inside the effect | `react-hooks/exhaustive-deps` would flag `goToPage` as a missing dependency | The effect calls `navigate` inline, with the same search update and deps `[emptyPastFirst, page, navigate]` |
| F16: overview pending shows the loading line "in place of the lesson options only when the overview is ready" (ambiguous) | — | While the overview is pending, the whole picker is the loading line. While lessons are pending, the line shows under «Lesson» and that select is disabled |
