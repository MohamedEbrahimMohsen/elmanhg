# Plan — [E21.S12] Wave-2/3 follow-ups: audit stamping rule, tighter tests, docs

## Goal
Audit fields follow one rule that holds on every save path: `UpdatedBy` is the acting user when there is one, otherwise whatever the aggregate set, and it is never cleared. Stamping moves from the `Repository.SaveChangesAsync` loop into an opt-in EF `SaveChangesInterceptor` in `Core.EntityFrameworkCore`, registered on `AppDbContext`. The interceptor runs inside `base.SaveChangesAsync`, after `CoreDbContext` has published domain events, so rows that event handlers add or change are stamped too. Aggregates stop deriving `UpdatedBy` from owner properties such as `StudentId` and `TeacherId`. The weak tests from waves 2 and 3 are tightened, and the test files and `SweepWorker.cs` that are over the size guide are split without losing a test or changing behaviour. `docs/audit-log.md`, `docs/constitution.md` and the dotnet skill describe the new rule.

## Scope
**In:** all four sub-tasks of #329 (UpdatedBy rule and aggregate fixes; interceptor stamping after dispatch; tightened tests and file splits; docs).
**Out:** `CoreDbContext` (no change, by dev decision). No migration. `CreatedBy` precedence does not change. #328 areas: OTP cooldown and columns, `Core.Storage.S3`, the cache default-TTL setting, the `CachingBehaviour` registration test in `PipelineCompositionTests`, the SMS client name, and the Resend retry tests. `SweepWorkerTests.cs`, which the story does not ask to split.
**Deferred:** none.

## Decisions
| # | Question | Decision | Why |
|---|----------|----------|-----|
| 1 | The UpdatedBy rule | On every Added, Modified or Deleted `AuditEntity` row: if `ICurrentUser.UserId` is not null, `UpdatedBy = actor`. Otherwise `UpdatedBy` keeps what the aggregate set, or its old value. It is never set to null by stamping. | This is the rule the story states. Stamping always assigns when there is an actor, so `IsModified` no longer matters for `UpdatedBy`, and the "aggregate set the value it already had" bug disappears. |
| 2 | Added rows: does the actor overwrite an aggregate-set `UpdatedBy`? | Yes, the same rule as for Modified rows. `CreatedBy` keeps `??= actor` (the aggregate's value wins). | The story defines one `UpdatedBy` rule. `CreatedBy` is outside the story, so "behaviour must not change" applies to it. |
| 3 | `UpdationDate` | The E21.S2 rule stays: on Modified or Deleted rows, stamp `now` only when `UpdationDate` is not `IsModified`. On Added rows, `CreationDate = now` with no condition. | Kept on purpose. A method that receives the transition instant stamps it, and `content-retrieval` staleness relies on that. |
| 4 | Where stamping lives | New `Core.EntityFrameworkCore.Auditing.AuditStampingInterceptor : SaveChangesInterceptor`, plus the opt-in `AddCoreAuditStamping<TContext>()`, which uses EF 10 `ConfigureDbContext<TContext>((sp, o) => o.AddInterceptors(...))`. The app calls it in `Program.cs`. | EF interceptors run inside `DbContext.SaveChangesAsync`. `CoreDbContext.SaveChangesAsync` publishes events first and then calls `base.SaveChangesAsync`, so stamping now comes after dispatch, and `CoreDbContext` stays unchanged. `ConfigureDbContext` (EF 9+, verified in EF 10.0.5) adds the interceptor without changing `AddCoreIdentity`'s `Action<DbContextOptionsBuilder>` signature. Core stays app-agnostic. |
| 5 | The repository loop | Removed. `Repository<T>.SaveChangesAsync` only saves. `Repository<T>` and every subclass lose the `ICurrentUser` and `TimeProvider` constructor parameters (5 core repositories and 33 app repositories). | If both stamped, there would be two stampers with two orders. Keeping the parameters unused would be dead code, and E21.S2 already removed dead code. All 38 subclasses use those parameters only to forward them to the base, which was verified with grep. |
| 6 | Interceptor lifetime and dependencies | `TryAddScoped<AuditStampingInterceptor>()`. Constructor `(ICurrentUser? currentUser = null, TimeProvider? timeProvider = null)`. MS DI supplies the defaults when a service is not registered. `TryAddSingleton(TimeProvider.System)`. | `ICurrentUser` is scoped. Options for `AddDbContext` are scoped by default, so the `sp` in `ConfigureDbContext` is the scope provider. A plain (not singleton) `IInterceptor` instance per scope is not part of EF's service-provider cache key. |
| 7 | How values are written | Through `entry.Property(x => x.UpdatedBy).CurrentValue = …` and `entry.Property(x => x.UpdationDate).CurrentValue = now`, not through the entity setter. | This marks the property modified immediately, whatever the order of EF's interceptor and `DetectChanges`. `ChangeTracker.Entries<AuditEntity>()` already runs `DetectChanges` first, so the `IsModified` check on `UpdationDate` is accurate. |
| 8 | Owner-derived `UpdatedBy` assignments (grep `UpdatedBy = StudentId\|TeacherId`) | Remove all 8: `QuestionMastery.Record`, `AvatarConversation.RecordExchange` and `.Delete`, `Session.Touch` (the `Resume` path), `TeacherThread.FollowUp` and `.Rate`, `ReviewSession.RecordOpening`, and `TeacherVoiceDraft.MarkSent`. Keep every assignment that comes from an actor argument (`updatedBy`, `deletedBy`, `teacherId`, `assignment.TeacherId` and similar). | An owner is not an actor: in teacher review and in grading workers the owner did not do the update. Owners already have their own columns (`StudentId`, `TeacherId`), so no new property and no migration are needed. The HTTP callers of the 7 non-mastery methods are always the owner, so the persisted value does not change there. `QuestionMastery` now records the teacher in review (as the story asks) and keeps the previous value in workers. |
| 9 | Domain rule wording | "A domain method sets `UpdatedBy` only from an actor argument it receives, never from an owner property." This goes into the SKILL, the constitution and `docs/audit-log.md`. | One rule, written once, in each place the docs-sync map names. |
| 10 | Existing tests whose expectation the story reverses | `RepositoryAuditStampingTests.SaveChangesAsync_ModifiedWithUpdatedBySet_KeepsAggregateActor` becomes `…_StampsActingUser`. `…_AddedWithCreator_KeepsCreatedBy` becomes `…_KeepsCreatedByAndStampsActingUserAsUpdatedBy`. `QuestionMasteryTests.Record_NewAttempt_StampsUpdatedBy` becomes `…_LeavesUpdatedByToTheSave`. Five domain tests change their `UpdatedBy` expectation (see Test plan). | The story mandates these changes, and the tests are not being weakened to pass. The test-integrity guard should treat them as intended. |
| 11 | How the core tests run the interceptor without a database | The probe context adds `AuditStampingInterceptor` and then `SuppressedSaveInterceptor`, which returns `InterceptionResult<int>.SuppressWithResult(0)`. EF calls interceptors in registration order and skips the database when a result is supplied. The probe's `SaveChangesAsync` publishes events with `DomainEventDispatcher.PublishAsync` before calling `base`, in the same order as `CoreDbContext`. | This is deterministic and runs offline, and it exercises the real EF pipeline. It also shows the after-dispatch ordering without needing a `CoreDbContext` (Identity generics). |
| 12 | Proving it end to end on the real `AppDbContext` | New integration tests save an `ExamPeriod` directly through `AppDbContext`, with no repository, with and without an acting user. The acting user is set through `IHttpContextAccessor.HttpContext`, which is what `CurrentUserService` reads. | They show that the app registration works and that the `IsModified` bug is fixed against PostgreSQL. No app event handler adds an `AuditEntity` today (training records are `Entity`), so the after-dispatch path is proven in core. |
| 13 | Shared harness for the split test files | An `abstract` base class per split (`AuditStampingTestBase`, `RefreshTokenRotatorTestBase`, `CachingBehaviourTestBase`) and a static constants class for `ConflictMap` (`ConflictMapProbe`). Protected fields use the `_` prefix, as in `Repository<T>`. | This is the only way to stay near 100 lines per file without duplicating setup. All method names move unchanged. |
| 14 | `RefreshTokenRotationRegistrationTests`: what "the value the registered options actually resolve to" means | Resolve `IRefreshTokenRotator<User>` from the container built by `AddCoreRefreshTokenRotation<User>()` and drive it. A replay exactly 10 s old gets a token, and a replay 11 s old is revoked. | Reading `IOptions<>.Value` without configuration only re-reads the class default. Driving the resolved rotator checks the value that the registered options give to the consumer. |
| 15 | `SweepWorker.cs` split | Make it `partial`. `SweepWorker.cs` keeps the surface, `ExecuteAsync` and `SweepAsync`. The new `SweepWorker.Steps.cs` holds the four guarded `Try*` steps, which use the existing protected `ScopeFactory` and `Logger` properties. No logic changes. | The story asks to extract helpers with no behaviour change. Partial types are an established pattern (`Lesson.Lifecycle.cs`, `AppDbContext.*.cs`). |
| 16 | Overlap with the parallel lane #328 | Expected merge points: `OtpRepository.cs` (only its constructor line changes here), `CachingBehaviourTests.cs` (this story owns the split), and `RuntimeSettingRegistryTests.cs` (a new test method only). | The caller assigned this ownership. Each edit is small and local. |
| 17 | Morabh reuse | The interceptor is new and has no Morabh equivalent. Morabh `Core/Core.EntityFrameworkCore/Repositories/Repository.cs` `SaveChangesAsync` is the origin of the loop being moved. | Reuse-first: this records where the code came from. |
