# Plan — Quiz screen with immediate feedback (#76, E5.S3)

## Goal
A student opens a lesson's practice screen, picks 5, 10 or 20 questions and starts (or resumes) a quiz. They answer one question at a time in a touch-friendly renderer for all five v1 types, press "تحقّق", and see the verdict, score, correct answer and explanation straight away, plus an "اسأل المساعد" button. Moving to the next question makes no network request. At the end, or at any time through "إنهاء التدريب", they see a result screen with score out of 100, time taken and a review of each answered question. A refresh resumes at the current position.

## Scope
**In:** `web/` only. New feature `web/src/features/quiz/` with 3 routes: `/student/lesson/$lessonId/practice`, `/student/quiz/$sessionId`, `/student/quiz-result/$sessionId`. A `review` (correct/wrong option) state added to the existing `QuestionView`/`ChoiceAnswerInputs` from #65. Session error strings in the shared locale files. A short "Student screens (web)" section in `docs/sessions.md`.
**Out:**
- API changes: none needed. `SubmitAnswerHandler` already returns `SessionResultGenerator.GenerateItem`, which carries `correctAnswer` (the served grading spec) and `explanation` only once an attempt exists or the session is finished (`api/Elmanhg.Application/Sessions/Shared/SessionResultGenerator.cs`, `reveal = attempt is not null || session.IsSubmitted`). OpenAPI, the Orval client and Postman stay unchanged.
- The lesson page with its الشرح/الأهداف/الملخص/التدريب sub-tabs, breadcrumbs with the lesson name, and "العودة للدرس": these belong to #85 (E7.S1). No student lesson-read endpoint exists yet. #85 embeds the exported `PracticeStart` component in its التدريب tab.
- Free-tier daily counter and paywall (#87). "اسأل معلّم" (E9). Difficulty chip: `SessionItemResult` has no difficulty, and it is question metadata, not part of the served revision.
- A working AI Avatar (E8, #91). The button is rendered disabled here (Decision 7).
**Deferred:** none.

## Decisions
| # | Question | Decision | Why |
|---|----------|----------|-----|
| 1 | Does submit-answer return the answer key and explanation? | Yes, already. No API change. The web reads `SessionItemResult.correctAnswer` and `.explanation` from the submit response and from `GET` after an attempt or finish. | Verified in `SessionResultGenerator.GenerateItem` and `docs/sessions.md` "What is revealed". |
| 2 | Prefetch mechanism for transitions under 300 ms | (a) `POST /api/sessions/quiz` already returns the full `SessionResult` with every item's stem and body. `useStartQuiz` writes it into the cache (`queryClient.setQueryData(getGetSessionQueryKey(id), session)`) before navigating, so the quiz page renders with no `GET`. (b) The quiz page reads the session with `staleTime: Infinity`; answers and finish update the cache with `setQueryData`, so there is never a background refetch. (c) "التالي" is a local state change: no request at all. (d) The images of the next item (stem and option HTML) are preloaded during render with React 19 `preload(src, { as: 'image' })` from `react-dom`. | Every item is fixed at start (#74), so there is nothing to fetch per question except images. Testable without timing: after "Next" the next heading is asserted with synchronous `getByRole`, not `findBy`, and the preload `<link>` is asserted in `document.head`. |
| 3 | Which question is shown? | Local UI state `position`, initialised once with `useState(() => initialPosition(session))`: `currentPosition` when set, otherwise the last position (every item answered but not finished). It is never synced from query data afterwards, so the cache update after an answer never moves the screen off the feedback. `mergeAnsweredItem` still recomputes `currentPosition` in the cache, so a remount resumes at the right place. | This follows #74 resume semantics: a refresh lands on the lowest unanswered position. It needs no effect-based syncing. |
| 4 | The answer shown for an answered item | Derived at render: `item.attempt ? fromAnswerPayload(question, item.attempt.answer) : localAnswer`. | After a resume or a 409 refetch, the saved answer is the truth. There is no state mirroring. |
| 5 | Practice sizes and `SessionsOptions` bounds | Constant `quizSizes = [5, 10, 20]` and `defaultQuizSize = 10` in `api/quizSession.ts`, commented as mirroring `Sessions:MinQuizSize`/`DefaultQuizSize`/`MaxQuizSize` (5/10/20; `docs/sessions.md` "Options"). A misconfigured server answers 422 `SESSION_QUESTION_COUNT_INVALID`, which shows inline. There is no options endpoint. | `docs/sessions.md` already says "The UI offers 5, 10 and 20". An endpoint for three constants is unneeded surface. |
| 6 | Resume from the practice screen | Any size button calls start. The server returns the open session for the lesson and ignores the count (#74), and the page navigates to it, landing on the current position. A caption tells the student this. | #74 semantics. There is no extra UI state. |
| 7 | "اسأل المساعد" before E8 | `AskAvatarButton` renders a disabled secondary pill button (Sparkles icon in accent), labelled "اسأل المساعد", with `aria-describedby` pointing at a visible caption "المساعد الذكي متاح قريبًا.". It takes no props. E8 (#91) adds the context props and an `onClick` that opens the AssistantSheet. It sits inside `FeedbackPanel`, so both the quiz screen and the result review get it. | A disabled button cannot show a hover tooltip on touch, so the visible caption is accessible and honest. There is no dead route. |
| 8 | Empty answer on "تحقّق" | The button stays enabled. An empty answer shows the inline `role="alert"` "أجب عن السؤال أولًا." and sends nothing. The alert clears when the answer changes. | React guide §9: never disable submit because input is invalid. Prototype `isEmpty`. |
| 9 | Emptiness per type | Mcq/Multi: no option; TrueFalse: `null`; Fill: every blank blank after trim; Short: text blank after trim. | Prototype `isEmpty`. |
| 10 | `timeTakenMilliseconds` | The client sends `Math.max(0, Date.now() - shownAt)`, where `shownAt` is `useState(() => Date.now())` in the card, which is keyed by position and so remounts per question. | The server clamps to its own elapsed time (#74). The client value excludes the time spent reading the previous question's feedback. |
| 11 | Mutation toasts | Answer, finish and new-practice success give no toast: the feedback panel (`role="status"`) or the navigation is the confirmation. Answer and finish errors show `toast.error(common:errors.<code>)` and `invalidateQueries(getGetSessionQueryKey(id))`. Start errors are inline on the practice card. | React guide §12: toasts are for transient outcomes; the verdict is persistent inline content. Invalidation resolves 409 `SESSION_QUESTION_ALREADY_ANSWERED`, `SESSION_MODIFIED_CONCURRENTLY` and 400 `SESSION_ALREADY_SUBMITTED`, the last by redirecting to the result. |
| 12 | Finished or open session on the wrong route | QuizPage with `submittedAt !== null` renders `<Navigate to="/student/quiz-result/$sessionId" replace>`. QuizResultPage with `submittedAt === null` renders `<Navigate to="/student/quiz/$sessionId" replace>`. | This keeps each URL meaningful after refresh or back navigation. |
| 13 | Last question | After feedback on the last item, the primary button reads "عرض النتيجة" and calls finish. Mid-quiz "إنهاء التدريب" is shown only before checking the current question, with no confirm dialog. | Prototype `vQuiz`. |
| 14 | Result review content | Only answered items, as in the prototype `vQuizResult`. Each shows `QuestionView` disabled with the student's answer and review states, then `FeedbackPanel`. If nothing was answered, the line "لم تُجب عن أي سؤال في هذا التدريب." is shown. The answered count "أجبت عن X من N" is always shown. | Prototype. |
| 15 | "تدريب جديد" size | It starts a new quiz for `lessonIdOf(session)` with `nextQuizSize(items.length)`: the smallest of 5/10/20 that is ≥ the served count, else 20. It is hidden when the scope has no `lessonId`. | This reproduces the requested size (a small pool gives the same shorter quiz again) and never sends a count out of bounds. The prototype restarts with the same count. |
| 16 | Displayed numbers | Student-facing digits are Arabic-Indic (`formatNumber(..., 'arabic-indic')` or ICU `{x, number}`). Score out of 100 is rounded to 0 fraction digits. Time is `splitDuration(totalMs)`: whole seconds rounded, then minutes and seconds. Numeric correct answers are wrapped in `<bdi>`. | Per the design-system RTL rules. |
| 17 | Correct-answer rendering | Mcq: the correct option's rich text. Multi: every correct option, in body order. TrueFalse: صح/خطأ. Fill: the first accepted answer of each blank, in body order ("الفراغ 1: …"). Short numeric: the value, plus "± tolerance" (or "± tolerance%") when tolerance > 0. Short text: the first accepted answer. A malformed or null spec renders nothing. Choice questions also colour the options: the correct option in success, a chosen wrong option in danger, each with an icon and sr-only text (colour is never the only signal). | Prototype `correctText` plus the design-prompt QuizOption states. |
| 18 | Unknown question type in a session | `toQuizQuestion` throws (a zod parse error). The page's route error boundary (`RouteError`) shows it. | Only the five v1 types are servable. No speculative UI. |
| 19 | Empty session | Not handled. The server never creates a session without items (`SESSION_NO_SERVABLE_QUESTIONS`). The practice screen's empty state covers "no questions". | React guide §12: the empty state lives where emptiness can occur. |
| 20 | Where the practice UI lives | `components/PracticeStart.tsx` (the card) is exported from the barrel. `pages/PracticePage.tsx` wraps it with the h1 at `/student/lesson/$lessonId/practice` (prototype route). No nav entry: #85 links it from the lesson page. | The lesson page is #85. |
| 21 | Feedback enter motion | Tailwind v4 `starting:opacity-0 transition-opacity duration-(--ds-motion-base-duration) ease-(--ds-motion-base-easing)`. Reduced motion is already zeroed globally in `app.css`. | The design system specifies FeedbackPanel enter as a fade at motion.base. These are token variables, not literals. |
| 22 | Morabh reuse | New — no Morabh equivalent. Morabh (`/home/user/apis`) is backend-only, has no `.tsx` and no quiz code. | Checked. |

`docs/sessions.md` section text (the implementer pastes it; wording may be tightened, facts may not change):
- Routes: `/student/lesson/{lessonId}/practice` (choose 5, 10 or 20; start or resume), `/student/quiz/{sessionId}` (one question at a time), `/student/quiz-result/{sessionId}` (score out of 100, time, review of answered questions). A finished session opens the result; an open one opens the quiz.

## API surface
Consumed only, through the generated hooks in `web/src/shared/api/generated/sessions/sessions.ts` (policy `Assessments.Take`):
- `POST /api/sessions/quiz`: `useStartQuizSession`, body `StartQuizSessionCommand { lessonId, questionCount }`, response `SessionResult`.
- `GET /api/sessions/{sessionId}`: `useGetSession`, key `getGetSessionQueryKey(sessionId)`, response `SessionResult`.
- `POST /api/sessions/{sessionId}/answers`: `useSubmitSessionAnswer`, body `SubmitAnswerRequest { questionId, answer, timeTakenMilliseconds }`, response `SessionItemResult` (with `attempt`, `correctAnswer`, `explanation`).
- `POST /api/sessions/{sessionId}/finish`: `useFinishSession`, response `SessionResult`.
